CS33001 · The Problem02

"It works on my machine."

For thirty years the most expensive class of bug was not logic — it was environment. The same code, on a second machine, simply stopped working.

Without Docker

  • Manual installs per machine — versions drift within a week
  • A dependency upgrade breaks one app, silently heals another
  • Setup takes a new hire days; nobody documents the quirks
  • Production is rebuilt from scripts nobody has ever tested
→

With Docker

  • One image carries the OS, libraries, and app together
  • Dependencies are isolated per container — no collisions
  • Onboarding is docker compose up
  • What CI tests is byte-for-byte what production runs

CS33004 · Origin Story05

Who created Docker?

Docker began as an internal project at dotCloud, a Platform-as-a-Service company founded by Solomon Hykes in 2010.

  • In March 2013, dotCloud open-sourced Docker at PyCon
  • By standardizing application environments, it gained industry-wide adoption rapidly
  • dotCloud eventually rebranded as Docker Inc.
  • Docker drastically simplified application deployment, paving the way for DevOps and cloud-native development

Why It Mattered

Before Docker, consistent deployment across development, staging, and production was a manual, error-prone process.

Docker gave engineers a single artifact that worked identically everywhere.

CS33005 · Why Docker Was Created06

Why was Docker created?

Docker addressed key challenges in traditional software engineering that had plagued deployment for decades.

"Works on my machine"

Software ran in development but failed in staging/production due to missing dependencies, library mismatches, or OS level anomalies.

Configuration Drift

Servers diverged over time as patches and updates were applied manually, making environments unpredictable and irreproducible.

Dependency Conflicts

Running multiple applications on the same host often caused version collisions (e.g., App A uses Python 2, App B uses Python 3).

Complex Deployments

Deploying apps required fragile scripts, runbooks, and manual intervention, leading to high downtime and frequent failures.

CS33006 · Why Engineers Use Docker07

Why software engineers use Docker.

Reproducibility

Maintains an identical and consistent environment across development, testing, staging, and production without drift.

Dependency Isolation

Packages all underlying code, libraries, and binaries into an isolated object to avoid conflicts between project dependencies.

Portability

Build it once, run it anywhere. Containers run seamlessly on any machine that supports and has the Docker Engine installed.

Faster Turnaround

CS33007 · Docker vs Virtual Machines08

Docker vs Virtual Machines.

Containers and VMs both provide isolation, but they work fundamentally differently.

Virtual Machines

  • Full OS per VM — entire kernel, libraries, and binaries
  • Heavy: GBs of disk, minutes to boot
  • Strong isolation via hypervisor
  • Best for: running different OSes, legacy apps, strict security boundaries
vs

Docker Containers

  • Shares host OS kernel — only app + dependencies packaged
  • Lightweight: MBs of disk, milliseconds to start
  • Process-level isolation via namespaces/cgroups
  • Best for: microservices, CI/CD, cloud-native apps, rapid iteration

CS33008 · Docker Components09

Docker components.

Images

Read-only templates built from Dockerfiles. Images are immutable and composed of layers — each instruction in the Dockerfile creates a new layer, enabling efficient caching and reuse.

Containers

A running instance of an image. Containers are isolated from each other and the host using Linux namespaces and cgroups. Each container has its own filesystem, network interface, and process tree.

Dockerfile

A text file containing a series of instructions to build an image. Key commands: FROM (base image), RUN (execute command), COPY (add files), CMD (default command).

# Dockerfile example
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
CMD ["node", "server.js"]

CS33009 · Docker Compose10

Docker Compose.

Define and run multi-container applications with a single YAML file. Compose handles networking, dependencies, and orchestration automatically.

Our Demo Stack

Three services defined in docker-compose.yml:

  • web — Nginx serving the frontend and proxying API requests
  • api — Node.js REST API handling business logic
  • db — PostgreSQL database with a persistent volume

Key features:

  • Services communicate over a shared Docker network
  • Database depends on API starting first (dependency ordering)
  • Data persists across container restarts via named volumes

# One command
$ docker compose up

# Starts all 3 containers
✓ web running
✓ api running
✓ db running

# Visit
http://localhost:8080

CS33010 · Real-World Use Cases11

Real-world use cases.

Where containerization shines in modern software engineering.

Microservices Architecture

Decompose monolithic applications into independent services that scale individually and communicate via APIs.

Example: Decoupling authentication from inventory management.

CI/CD Pipelines

Provide identical environments for building, testing, and production deployment, eliminating configuration drift completely.

Example: Automated GitHub Actions runners using Docker.

Environment Consistency

Solve "it works on my machine" by encapsulating runtimes and dependencies in version-controlled declarative files.

Example: A new dev instantly spinning up a local replica stack.

Legacy App Modernization

Pack legacy enterprise apps with older dependencies into containers to host them on the modern cloud without rewriting.

Example: Containerizing legacy Java software for GCP/AWS.

CS33011 · Live Demo Walkthrough12

Live demo walkthrough.

We'll demonstrate Docker's key capabilities with our three-container stack.

01

Start the stack

Run docker compose up --build -d — builds images, starts all three containers in dependency order, and runs them in the background.

02

Verify running containers

Run docker compose ps — shows all three services healthy and running. Visit localhost:8080 to see the live app.

03

Demonstrate persistence

Add data via the web UI, then run docker compose down (stops and removes containers). Restart with docker compose up -d — the data survives because it's stored in a named volume.

Conclusion.

Docker enabled the DevOps movement, cloud-native architecture, and microservices at scale. It transformed deployment from a manual, error-prone process into a reproducible, automated workflow.
